# PatWiki 升级总体项目规划文档

> **文档版本**: v1.0  
> **创建日期**: 2025-01  
> **基于**: PatWiki vs 飞书多维表格功能架构对比分析报告  
> **项目仓库**: github.com/Casafred/patwiki

---

## 一、项目背景与目标

### 1.1 项目定位

PatWiki 是一款**专利领域本地优先的多维表格工具**，基于 Tauri 桌面应用架构（Python/FastAPI 后端 + React/TypeScript 前端 + Rust 壳），采用 SQLite 本地数据库，面向企业专利管理部门提供数据导入、标注、分析、协作的全流程支持。

### 1.2 升级动因

通过与飞书多维表格的 9 维度 43 项功能对比，PatWiki 当前功能覆盖度约 **35%**，存在 **12 项关键差距**（7 项 Must-Have + 5 项 Should-Have）。本次升级旨在：

1. **补齐多维表格核心骨架能力**（公式字段、关联字段、数据导出、视图多样性）
2. **引入专利场景自动化能力**（规则引擎、定时触发）
3. **清理架构技术债务**（Alembic 迁移、前端路由重构）
4. **保持并深化专利垂直差异化优势**（Wiki 式增量合并、同族聚拢、AI 字段抽取）

### 1.3 升级原则

| 原则 | 说明 |
|------|------|
| **本地优先不变** | 所有新功能基于 SQLite 本地存储，不引入云端依赖 |
| **向后兼容** | 新增字段类型/视图类型采用枚举扩展，不破坏现有数据 |
| **增量交付** | 分三期实施，每期可独立交付验证 |
| **垂直深化** | 补齐通用能力的同时，持续深化专利场景差异化 |
| **架构先行** | 数据模型层改造优先于视图层和 UI 层 |

### 2.3 PatWiki 独有优势（保持项）

| 优势项 | 说明 |
|--------|------|
| Wiki 式增量合并 | 著录字段覆盖 + 标注字段保护，飞书不具备 |
| 同族/引用关系解析 | MD5 哈希 family_id + 占位专利创建 |
| AI 批量字段抽取 | OpenAI 集成 + 任务追踪 + 人工覆盖 |
| 专利法律状态建模 | 10 种 LegalStatus 枚举映射专利生命周期 |
| 本地优先架构 | 数据不出本机，隐私合规 |
| 一键聚拢同族 | 列表页同族折叠展示 |

## 三、三期实施路线图

### 第一期：Must-Have 核心（2-3 周）

**目标**: 解决用户最痛的公式计算和数据导出，补齐多维表格基础视图能力

| 周次 | 任务 | 交付物 |
|------|------|--------|
| W1 | 公式字段引擎（AST 解析 + 依赖图 + 增量更新） | FormulaFieldHandler + ExpressionEngine + DependencyGraph |
| W1 | 数据导出（pandas to_excel + 视图筛选导出） | ExportService + API 端点 + 前端导出按钮 |
| W2 | 看板视图（view_type 扩展 + KanbanView 组件） | PatentView.view_type 枚举扩展 + KanbanView.tsx |
| W2 | 条件格式（规则引擎 + 着色渲染） | ConditionalFormatRule 模型 + 前端着色逻辑 |
| W3 | 集成测试 + 文档更新 | 测试报告 + API 文档 |

### 第二期：Must-Have 扩展（3-4 周）

**目标**: 补齐关联字段体系和高级视图，完成多维表格核心功能闭环

| 周次 | 任务 | 交付物 |
|------|------|--------|
| W1-W2 | 通用关联字段模型（CrossTableLink + Lookup + Rollup） | CrossTableLink 模型 + LookupService + RollupService |
| W3 | 表单视图（form_config + FormView 组件 + 分享链接） | FormView.tsx + form_config JSON 结构 |
| W4 | 甘特视图（Date 字段映射 + frappe-gantt 集成） | GanttView.tsx + 日期字段配置 |
| W4 | 分组 Group-by（后端 group_by + 前端折叠展示） | ViewService 分组逻辑 + 前端分组渲染 |

### 第三期：Should-Have 智能化（3-4 周）

**目标**: 引入自动化和协作能力，形成差异化竞争力

| 周次 | 任务 | 交付物 |
|------|------|--------|
| W1-W2 | 自动化规则引擎（Trigger→Condition→Action + Webhook） | AutomationRule 模型 + RuleEngine + 预置专利模板 |
| W3 | 附件字段（本地文件存储 + 预览） | AttachmentField 类型 + 文件管理服务 |
| W3 | 可配置仪表盘（Dashboard 模型 + ECharts） | Dashboard 模型 + DashboardPage.tsx |
| W4 | 评论系统 | Comment 模型 + 评论 Tab |
| W4 | 架构债务清理（Alembic + react-router） | Alembic 迁移脚本 + 路由重构 |

**预计总工期**: 8-11 周（含测试与文档更新）

## 四、技术选型总览

### 4.1 后端技术栈

| 技术 | 用途 | 现状 | 升级计划 |
|------|------|------|---------|
| Python 3.11+ | 运行时 | ✅ 已使用 | 保持 |
| FastAPI | Web 框架 | ✅ 已使用 | 保持 |
| SQLAlchemy 2.0 | ORM | ✅ 已使用 | 保持 |
| SQLite | 数据库 | ✅ 已使用 | 保持（本地优先） |
| Alembic | 数据库迁移 | ❌ 未使用 | 第三期引入 |
| pandas | 数据导出 | ❌ 未使用 | 第一期引入 |
| openpyxl | Excel 导出 | ❌ 未使用 | 第一期引入 |
| APScheduler | 定时任务 | ❌ 未使用 | 第三期引入 |
| Python AST | 公式解析 | ❌ 未使用 | 第一期引入 |

### 4.2 前端技术栈

| 技术 | 用途 | 现状 | 升级计划 |
|------|------|------|---------|
| React 18 | UI 框架 | ✅ 已使用 | 保持 |
| TypeScript | 类型系统 | ✅ 已使用 | 保持 |
| Vite | 构建工具 | ✅ 已使用 | 保持 |
| react-router-dom | 路由 | ⚠️ 已引入未启用 | 第三期启用 |
| frappe-gantt | 甘特图 | ❌ 未使用 | 第二期引入 |
| ECharts / Recharts | 图表 | ❌ 未使用 | 第三期引入 |
| @dnd-kit | 拖拽排序 | ❌ 未使用 | 第一期引入（看板拖拽） |
| react-hook-form | 表单 | ❌ 未使用 | 第二期引入（表单视图） |

### 4.3 架构决策记录

| ADR | 决策 | 理由 |
|-----|------|------|
| ADR-001 | 公式引擎使用 Python AST 而非 eval | 安全性：AST 可限制可调用函数白名单 |
| ADR-002 | 关联字段采用通用 CrossTableLink 模型 | 从专利-项目硬编码升级为通用跨表关联 |
| ADR-003 | 视图类型用 String 枚举而非 SQLEnum | 便于扩展新视图类型不需数据库迁移 |
| ADR-004 | 导出使用 pandas + openpyxl | 成熟稳定，支持多 sheet、格式化 |
| ADR-005 | 仪表盘使用 ECharts 而非 Recharts | 功能更强大，专利数据可视化场景更丰富 |
| ADR-006 | 自动化引擎基于 APScheduler | 轻量级，适合本地桌面应用场景 |

## 八、风险与缓解措施

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 公式引擎安全漏洞 | 高 | AST 白名单解析，禁止危险函数调用 |
| 关联字段循环依赖 | 高 | 依赖图检测循环，创建时校验 |
| SQLite 大数据量性能 | 中 | 增量更新 + 索引优化 + 分页加载 |
| 前端 PatentListPage 过大 | 中 | 按视图类型拆分子组件 |
| Tauri 打包体积增大 | 低 | 按需引入依赖，tree-shaking |
| 向后兼容性 | 高 | 枚举扩展 + JSON 配置 + 迁移脚本 |
