# PatWiki 外部专利数据同步与监控架构规范

> 状态：执行契约  
> 版本：1.0  
> 生效日期：2026-09-19  
> 适用范围：外部专利数据 API、MCP、法律状态更新、申请人/检索式监控、Webhook、定时同步及相关前后端功能  
> 读者：产品设计者、后端/前端开发者、测试人员和执行开发任务的 Agent

## 1. 文档地位

本文档既是目标架构设计，也是后续开发的强制实施契约。凡涉及以下任一范围，开发前必须完整阅读本文档：

- 接入专利数据服务商 API 或 MCP；
- 更新专利著录信息、法律状态、同族、引用等外部事实；
- 按申请人、检索式或其他条件持续发现新公开专利；
- 新增手动刷新、定时同步、Webhook 或规则触发；
- 新增外部数据的审查、冲突处理、来源追踪、通知或同步管理界面。

本文档与 `15-专利全局索引与表格检索契约.md`、`PatWiki_refactor_guidance_pack/21-implementation-contract.md` 同为执行契约。发生冲突时，必须选择更严格的数据保护、身份一致性和可追溯要求，不得自行降低标准。

本文使用以下规范词：

- **必须**：实现不可省略，否则不得合并或宣称完成；
- **禁止**：不得采用，即使短期实现更简单；
- **应当**：默认实现，偏离时必须在 PR 或设计记录中说明理由；
- **可以**：可选能力，不属于首期完成条件。

## 2. 背景与现状判断

PatWiki 当前采用 Tauri + React/Vite + FastAPI + SQLAlchemy + SQLite 的本地优先架构，并已具备以下可复用基础：

- `PatentIdentifier`：申请号、公开号、授权号和外部标识的统一身份索引；
- `PatentDatabaseMembership`：全局专利实体在多个业务库中的成员关系；
- `ImportSourceRow`、`FieldObservation`：来源证据、候选事实和人工审查；
- `SourceTableDefinition`、`FieldDefinition`、`SourceFieldMapping`：来源字段治理；
- `PatentHistory`：正式字段变化历史；
- `AutomationRule`、`AutomationLog`：已接受事实变化后的业务动作。

现有 Automation 调度器以周期轮询和逐专利执行为核心，适合“数据变化后执行动作”，不适合直接承担外部同步。外部同步还需要订阅、分页游标、快照、幂等、限流、断点恢复、字段所有权、来源冲突和任务级可观测性。

因此，本功能必须作为独立的 Connector/Sync 子系统建设，并位于现有审查和自动化流程之前。无需替换 SQLite，也不得为首期引入 Celery、Kafka、Kubernetes 或云端微服务。

## 3. 架构目标与非目标

### 3.1 目标

1. 以统一契约接入不同专利数据商，避免每个供应商形成独立业务流程。
2. 支持单件、批量、订阅检索、定时、内部事件和 Webhook 触发。
3. 所有外部数据都可追溯到供应商、请求、原始响应、映射版本和同步批次。
4. 重复同步、超时重试和任务恢复不产生重复专利、法律事件或通知。
5. 官方事实、派生结果、用户判断和 AI 建议有明确所有权边界。
6. 保持本地优先：断网时已有数据和核心操作仍可使用。
7. 同一套标准事实管道同时服务 API Connector 与 MCP Adapter。

### 3.2 非目标

- 首期不建设分布式任务平台或云端同步中心；
- 不允许 Provider 直接写入 `Patent` 或任意业务表；
- 不把 MCP 当成数据库管理接口或任意 SQL 通道；
- 不自动覆盖分类、风险结论、备注、项目关系等人工判断；
- 不在缺少认证、授权和审计边界时开放外网可写 MCP；
- 不以单个“当前法律状态”字符串替代法律事件时间线。

## 4. 总体架构

```text
Manual / Schedule / Rule / Webhook
                 |
          SyncSubscription
                 |
              SyncRun
                 |
       Connector capability contract
          /                    \
   REST/API Adapter         MCP Adapter
          \                    /
          ExternalSnapshot (immutable)
                 |
             Normalizer
                 |
       Patent identity resolution
                 |
      ExternalFactObservation
                 |
        Reconciliation Policy
          /                    \
 safe auto-apply          manual review
          \                    /
 Patent / LegalStatusEvent / Relations / History
                 |
             WatchEvent
                 |
       Automation / notification
```

组件职责必须严格分离：

| 组件 | 负责 | 不负责 |
|---|---|---|
| Connector | 鉴权、请求、分页、供应商错误转换、能力声明 | 身份合并、字段覆盖、直接写 Patent |
| Sync Orchestrator | 创建运行、领取租约、分页、重试、游标提交、统计 | 解释供应商字段业务含义 |
| Normalizer | 将供应商 payload 转为版本化标准事实 | 决定事实是否覆盖当前值 |
| Identity Resolver | 通过 `PatentIdentifier` 匹配、创建候选或报告歧义 | 仅凭模糊标题合并专利 |
| Reconciliation Policy | 按字段所有权、来源优先级和置信度决策 | 绕过审查直接写受保护字段 |
| Apply Service | 在事务中应用已接受事实并写历史 | 调用外部供应商 |
| Watch Service | 从已接受事实生成可去重业务事件 | 把每次抓取都当成变化通知 |
| Automation | 对已提交事实和 WatchEvent 执行业务动作 | 承担 Provider 分页同步 |

## 5. 后端模块边界

推荐目标结构如下；可根据仓库实际结构分阶段落地，但职责边界不得合并回单一大服务：

```text
backend/app/integrations/
  contracts.py          # Connector、能力和标准返回结构
  registry.py           # Connector 注册和实例化
  providers/            # 各供应商 API 适配器
  mcp/                  # MCP transport/adapter
  normalization/        # 号码、日期、法域、状态标准化

backend/app/sync/
  orchestrator.py       # 一次 SyncRun 的状态机和事务边界
  scheduler.py          # 到期 subscription 的领取与调度
  cursor.py             # cursor/watermark/overlap window
  reconciliation.py     # 字段所有权与冲突策略
  retry.py              # 重试、限流、熔断
  replay.py             # 基于快照重新标准化和应用

backend/app/watch/
  legal_status.py       # 事件标准化和当前状态投影
  query_monitor.py      # 保存检索式的增量监控
  event_service.py      # WatchEvent 生成、去重和确认
```

API 层只负责校验、授权边界、调用服务和序列化；不得包含供应商请求、同步编排或字段覆盖逻辑。

## 6. Connector 与标准数据契约

### 6.1 能力接口

```python
class PatentConnector(Protocol):
    def capabilities(self) -> ConnectorCapabilities: ...
    async def healthcheck(self) -> ConnectorHealth: ...
    async def search(
        self, query: CanonicalPatentQuery, cursor: str | None, limit: int
    ) -> SearchPage: ...
    async def fetch_patent(
        self, identifier: CanonicalPatentIdentifier
    ) -> ProviderPatentRecord: ...
    async def fetch_legal_events(
        self, identifier: CanonicalPatentIdentifier, cursor: str | None = None
    ) -> LegalEventPage: ...
```

每个 Connector 必须声明：

- `connector_code`、契约版本和适配器版本；
- 支持的法域、检索能力、字段、法律事件及增量方式；
- 分页模型、最大页大小、默认超时和速率限制；
- 是否支持单件刷新、批量检索、Webhook、按更新时间增量；
- 数据许可、允许保存的原始内容和建议保留期限；
- 错误分类映射和供应商时间语义。

### 6.2 标准记录最低字段

`ProviderPatentRecord` 至少能够表达：

- `provider_record_id`、`source_updated_at`、`source_version`；
- 原始及规范化的申请号、公开号、授权号、法域和文献种类代码；
- 标题、摘要、申请人、专利权人、发明人、优先权；
- 申请日、公开日、授权日；
- 法律事件列表或其独立抓取引用；
- 下一页游标、响应快照引用和字段级来源元数据。

标准结构必须使用 Pydantic 模型并版本化。供应商原始字段不得泄漏到业务服务中；新增 Provider 时优先扩展标准契约或保留 `provider_extensions`，不得在 `Patent.custom_fields` 中偷偷建立第二套事实模型。

## 7. 持久化模型

### 7.1 配置与订阅

| 表 | 关键字段 | 约束 |
|---|---|---|
| `connector_definitions` | `code`、`transport`、`endpoint`、`capabilities_json`、`config_json`、`enabled` | `code` 唯一；配置不得含明文密钥 |
| `connector_credentials` | `connector_id`、`credential_ref`、`credential_type` | 仅保存系统密钥引用 |
| `saved_patent_queries` | `database_id`、`name`、`query_json`、`query_version`、`query_hash` | 查询版本和 hash 不可省略 |
| `sync_subscriptions` | `connector_id`、`database_id`、`scope_type`、`scope_json`、`schedule_json`、`review_policy`、`enabled` | 调度单位必须是订阅 |
| `sync_cursors` | `subscription_id`、`cursor`、`watermark`、`overlap_seconds`、`provider_snapshot_version` | `subscription_id` 唯一 |

### 7.2 运行与证据

| 表 | 关键字段 | 约束 |
|---|---|---|
| `sync_runs` | trigger、status、cursor before/after、计数、rate-limit、错误摘要、时间 | 每次执行独立记录 |
| `sync_records` | run、external ID、identity result、outcome、idempotency key、错误 | `idempotency_key` 唯一 |
| `external_snapshots` | connector、request metadata、payload/hash、fetched_at、source version | 原始响应不可变；敏感字段脱敏 |
| `external_fact_observations` | snapshot、patent、canonical field、raw/normalized/current/candidate、confidence、decision | 观察不能因应用或忽略而删除 |
| `sync_dead_letters` | record/run、error class、retry count、replay state | 支持人工重放 |
| `sync_leases` | subscription、owner、expires_at | 每个 subscription 同时一个有效租约 |

### 7.3 业务结果

| 表 | 关键字段 | 约束 |
|---|---|---|
| `legal_status_events` | patent、event code/date、jurisdiction、source、provider event ID、snapshot | 追加式；Provider 事件唯一 |
| `watch_events` | event type、patent/query、severity、dedupe key、payload、ack state | `dedupe_key` 唯一 |

最低索引要求：

- `sync_subscriptions(enabled, next_run_at)`；
- `sync_runs(subscription_id, started_at)`；
- `sync_records(run_id, outcome)` 和唯一 `idempotency_key`；
- `external_snapshots(connector_id, payload_hash)`；
- `external_fact_observations(patent_id, canonical_field_key, status)`；
- `legal_status_events(patent_id, event_date)`；
- `watch_events(database_id, acknowledged_at, occurred_at)`。

所有表必须通过项目现有版本化迁移服务创建，迁移前备份并通过完整性检查；不得仅依赖 `Base.metadata.create_all()` 作为正式升级方案。

## 8. 身份、字段所有权与应用策略

### 8.1 身份解析

身份识别必须复用 `PatentIdentifier` 和统一号码规范化：

1. 精确命中一个 Patent：继续事实比较；
2. 未命中且存在可信官方标识：形成可创建候选，根据订阅策略自动创建或审查；
3. 多个标识命中不同 Patent：整条记录标记 `identity_conflict`，禁止部分应用；
4. 仅标题、申请人等模糊相似：只能给出候选，不得自动合并；
5. 不同法域的同族成员保持独立 Patent，以结构化同族关系关联。

### 8.2 字段所有权

| 类型 | 示例 | 默认策略 |
|---|---|---|
| 外部权威事实 | 官方号码、公开/授权日期、申请人、法律事件 | 身份明确、校验通过时可自动应用 |
| 派生投影 | 当前法律状态、最近状态日期、同族摘要 | 从接受事实重新计算，不作为独立权威来源 |
| 用户/内部字段 | 分类、模块、备注、项目关系、风险结论 | 禁止外部同步静默覆盖 |
| AI/草稿字段 | 摘要建议、分类建议、风险建议 | 只生成建议，必须标识来源和版本 |

出现以下情况必须进入人工审查：

- 身份歧义或标识冲突；
- 外部值试图清空已有非空值；
- 多个权威来源互相冲突；
- 低置信度、无法解析或未注册字段；
- 受保护的用户字段发生候选变化；
- 映射版本升级后产生与既有值不同的结果。

正式应用必须在同一事务中写入业务值、`PatentHistory`、观察决策和运行统计。失败时整体回滚，不能出现值已修改但来源未记录的状态。

## 9. 法律状态模型

法律状态必须以 `LegalStatusEvent` 追加式保存。`Patent.legal_status`、`legal_status_date` 只作为事件时间线计算出的当前投影和查询缓存。

供应商事件代码必须经过版本化映射转换为 PatWiki 标准事件。标准事件至少应区分：申请、公开、实质审查、授权、驳回、撤回、视为撤回、期限届满、未缴费失效、无效、终止、权利恢复及未知。

投影规则必须：

- 明确法域和事件生效日期；
- 保存原始事件描述和供应商代码；
- 对迟到、更正和撤销事件支持重新投影；
- 同一 Provider 事件重复到达时不重复插入；
- 投影发生实质变化时只生成一个去重后的 `WatchEvent`。

禁止仅比较供应商返回的当前状态字符串并覆盖本地状态，因为这会丢失时间线、来源和状态纠正依据。

## 10. 申请人和检索式监控

`SavedPatentQuery` 保存结构化、版本化检索条件，而不是只保存展示字符串。最低支持申请人、关键词/检索式、法域、公开日期范围和状态条件。

一次增量查询必须遵循：

1. 读取已提交 cursor 或 watermark；
2. 无稳定 cursor 时使用公开/更新时间水位，并回退一个可配置重叠窗口；
3. 分页抓取并逐页持久化快照和处理结果；
4. 以 Provider external ID 和专利正式标识双重去重；
5. 新专利建立全局 Patent 或目标数据库成员关系，不复制事实实体；
6. 仅对首次发现或实质变化生成 `WatchEvent`；
7. 当前页持久处理完成后提交 cursor。

检索式修改必须创建新版本和 hash。旧运行保留其实际使用的查询版本，禁止修改历史运行所引用的查询定义。

## 11. 触发与运行状态机

### 11.1 触发方式

- 手动：单件、选中专利、一个订阅、一个 Connector；
- 定时：按 `SyncSubscription.next_run_at` 领取到期任务；
- 内部事件：导入完成、数据超过新鲜度阈值、查询版本改变；
- Webhook：校验签名后创建运行，仍进入统一 Orchestrator；
- Automation：只能请求创建 SyncRun，不能绕过同步管道调用 Provider。

### 11.2 状态机

```text
queued -> running -> succeeded
                  -> partial
                  -> failed_retryable -> queued
                  -> failed_permanent
                  -> cancelled
```

状态迁移必须由 Sync Orchestrator 控制。`partial` 表示部分记录已持久完成且其结果可保留，不得伪装成完整成功。取消操作必须在安全检查点停止，不回滚已提交页面。

## 12. 幂等、游标、重试和恢复

### 12.1 幂等

推荐幂等键：

```text
sha256(connector_code + subscription_id + record_or_event_id + source_version_or_payload_hash)
```

相同键必须返回已有处理结果，不重复创建专利、事件、历史或通知。没有稳定外部 ID 时必须使用规范身份、事件日期/代码和 payload hash 的确定性组合。

### 12.2 游标提交

- Cursor 只在当前页快照、记录和观察全部持久化后推进；
- Cursor 更新与页面完成标记必须处于同一事务；
- 运行失败后从最后已提交 cursor 恢复；
- 日期水位必须使用重叠窗口抵御迟到数据；
- 禁止在发出请求后、写入结果前提前推进 cursor。

### 12.3 重试与限流

- 429 必须尊重 `Retry-After`；
- 超时、连接失败、429、502/503/504 属于可重试错误；
- 无效凭证、无权限、参数/Schema 错误默认属于永久错误；
- 重试采用指数退避加随机抖动，并设置最大次数和最长延迟；
- 每个 Connector 独立设置并发、QPS、每日配额和超时；
- 连续失败达到阈值时打开熔断器，健康检查通过后半开恢复。

### 12.4 SQLite 并发约束

本地调度使用数据库 lease，领取必须是原子更新。Lease 包含 owner 和到期时间，崩溃后可超时接管。不得依赖进程内布尔变量或仅依赖前端按钮禁用来防止重复运行。

## 13. 原始快照、重放与保留

每次外部响应必须先形成不可变 `ExternalSnapshot`，再进入标准化。快照至少保存脱敏请求元数据、状态码、抓取时间、内容类型、payload hash、供应商版本和原始内容或受许可约束的等价证据。

重放功能必须能够选择快照和新版 Normalizer，在不重新调用供应商的情况下重建观察。重放产生新的处理记录和映射版本，不修改旧快照、旧观察或旧决策。

若供应商许可禁止长期保存完整响应，Connector 必须声明保留策略，并至少保存可审计字段证据、hash、请求标识和字段级来源。禁止默认无限期保留密钥、Cookie、签名 URL 或个人敏感信息。

## 14. API 与 MCP 边界

### 14.1 应用 API 规划

```text
GET/POST/PATCH  /api/connectors
POST            /api/connectors/{id}/test
GET/POST/PATCH  /api/saved-queries
GET/POST/PATCH  /api/sync-subscriptions
POST            /api/sync-subscriptions/{id}/run
POST            /api/patents/{id}/refresh
GET              /api/sync-runs
GET              /api/sync-runs/{id}
GET              /api/sync-runs/{id}/records
GET/PATCH        /api/external-observations
GET              /api/patents/{id}/legal-events
GET/PATCH        /api/watch-events
POST             /api/sync-dead-letters/{id}/replay
```

批量启动接口返回 `SyncRun` 标识，不等待网络同步完成。列表 API 必须分页并提供稳定筛选；错误响应应包含机器可读错误码、是否可重试和关联 run/record ID。

### 14.2 MCP 规则

MCP 是语义化工具和传输边界，不是 Connector 业务规则的替代品。每个工具必须声明固定输入/输出 JSON Schema、版本、超时、分页、最大行数、审计级别、权限范围和新鲜度要求。

禁止提供：

- 任意 SQL 执行；
- 任意表名、字段列表或文件路径访问；
- 绕过身份、观察、审查和历史的直接写入；
- 默认自动确认的责任性法律结论或风险结论。

首批 MCP 工具应为只读语义工具，例如 `search_patents`、`get_patent`、`get_legal_events`。写工具必须默认创建候选或草稿，并在认证、授权和通用审计能力完成后才能对外开放。

## 15. 前端信息架构

前端至少规划以下入口：

| 位置 | 功能 |
|---|---|
| 设置 / 数据源 | Connector 配置、密钥状态、能力、健康检查 |
| 设置 / 同步订阅 | 范围、检索式、频率、审查策略、启停 |
| 数据库 / 监控检索 | 申请人和查询条件、最近发现、下次运行 |
| 同步中心 | Run 状态、统计、错误、限流、重试和明细 |
| 待审查变更 | 当前值与候选值、来源、置信度、批量决策 |
| 专利详情 / 数据来源 | 最近同步、字段来源、刷新操作 |
| 专利详情 / 法律事件 | 可排序时间线、原始代码、来源和投影状态 |
| 通知 / 监控事件 | 新公开、授权、失效等变化及确认状态 |

运行中的同步必须可离开页面继续执行；前端轮询或事件更新只负责展示，不得成为任务执行载体。批量操作必须预先显示影响数量，失败项不得从列表中消失。

## 16. 凭证与安全

第一阶段定位为本地单用户连接器，但仍必须遵守：

- API Key、OAuth refresh token 等放入 Windows Credential Manager 或跨平台 keyring；
- SQLite 只保存 `credential_ref` 和非敏感配置；
- 日志、快照和错误信息必须移除 Authorization、Cookie、token、签名参数；
- Connector 健康检查不得返回密钥或完整敏感请求；
- Webhook 必须校验签名、时间窗口和重放标识；
- SSRF 防护应限制 Connector endpoint 的协议和配置来源；
- 未完成服务端认证、授权和审计前，禁止监听公网或开放外部 MCP 写入。

供应商数据许可、调用配额和保存条款是 Connector Definition 的发布门禁，不明确时不得把完整 payload 作为长期数据源使用。

## 17. 可观测性与用户可理解性

每个订阅必须可查询：最近尝试、最近成功、下次运行、数据新鲜度、当前游标和连续失败次数。每次运行至少统计：读取、去重、创建、更新、无变化、待审查、失败、重试和 WatchEvent 数量。

错误必须回答三个问题：哪个 Connector/订阅失败、失败在哪个阶段、用户是否需要操作。日志使用 run ID、record ID 和 snapshot ID 关联，不得只记录自由文本异常。

## 18. 开发阶段与完成定义

### Phase 1：Provider-neutral 基座

- Connector 契约、注册表和模拟 Provider；
- 配置、订阅、运行、快照、观察、游标、租约和 dead letter 模型；
- 手动执行、幂等、分页恢复、重试和运行查询 API；
- 不修改 Patent 的端到端模拟同步。

完成标准：重复运行无重复证据；中断后从最后页面恢复；快照可重放；数据库重启不丢运行状态。

### Phase 2：首个真实 Provider 与单件同步

- 接入一个明确数据许可的真实 Provider；
- 单件专利和法律事件抓取；
- 身份解析、字段审查、受控应用和 PatentHistory；
- 专利详情的数据来源和法律事件时间线。

完成标准：用户字段不被覆盖；身份冲突不部分写入；状态事件可解释当前投影；失败不会破坏现有专利。

### Phase 3：订阅和申请人监控

- SavedPatentQuery、定时调度和增量游标；
- 新公开发现、数据库成员关系和 WatchEvent；
- 同步中心、订阅管理和待审查队列。

完成标准：重叠窗口不重复通知；检索式版本可追溯；定时与手动并发不会重复执行同一订阅。

### Phase 4：强化和 MCP

- Webhook、熔断、配额、保留策略和批量重放；
- MCP 只读工具和能力发现；
- 多来源优先级及更完整的冲突治理。

生产级 MCP 写入、多用户权限和云端任务调度必须另行评审，不包含在本阶段默认范围。

## 19. 强制测试门禁

每个实现 PR 必须按范围提供自动化测试。完整特性至少覆盖：

- Connector 契约测试和供应商 payload fixture；
- 标准化的号码、日期、法域和未知状态；
- 单一命中、未命中、多 Patent 冲突和跨法域同族；
- 同一页面、记录、法律事件和通知的重复执行；
- 分页第二页失败、恢复后不跳页也不重复应用；
- 429 `Retry-After`、超时重试、永久鉴权失败和熔断；
- Lease 过期接管及两个调度器竞争；
- 用户字段不可覆盖、清空值进入审查、多来源冲突；
- 法律事件迟到/更正后的当前状态重新投影；
- 查询重叠窗口、查询版本变更和新公开去重；
- 凭证不进入数据库明文、日志或快照；
- 迁移的空库、历史库、重复执行、失败恢复和完整性检查；
- 前端运行状态、空状态、失败重试、审查确认和详情时间线；
- 后端全量测试、前端 lint、TypeScript、生产构建和 `git diff --check`。

禁止只使用真实供应商在线接口完成测试。CI 和本地测试必须能够依靠固定 fixture、模拟服务器和可控时钟确定性运行。

## 20. 后续开发必须遵守的架构规则

以下规则是合并门禁：

1. Provider Adapter 禁止直接写 `Patent`、法律状态或用户字段。
2. 所有外部数据必须先有不可变来源快照，再形成标准观察。
3. 所有专利身份必须经 `PatentIdentifier` 服务解析，不得自行查询几个号码后猜测合并。
4. 法律状态必须保存事件时间线；当前状态只是可重建投影。
5. 用户和内部字段禁止被外部同步静默覆盖。
6. 每个 Provider 必须实现统一 Connector 契约及契约测试。
7. 调度单位必须是 `SyncSubscription`，禁止为数据库中的每件专利创建无界 API 轮询。
8. Cursor 只能在页面持久化完成后提交，所有处理必须可幂等重放。
9. API 与 MCP 必须共用标准事实和同步管道，不得形成两套写入逻辑。
10. MCP 禁止暴露任意 SQL、任意表/字段和无审查写入。
11. 密钥必须由系统凭证存储管理，禁止进入普通配置 JSON、日志或提交文件。
12. 首期保持本地优先和 SQLite 单实例约束；引入分布式基础设施必须有实测瓶颈和独立 ADR。
13. 新增字段、状态映射或覆盖策略必须版本化，并能解释历史运行使用的版本。
14. 任一失败都不得造成“业务值已更新但来源/历史缺失”的半提交状态。
15. 架构偏离必须先更新本文档或提交 ADR，说明动机、数据迁移、兼容、回滚和测试影响；不得先写代码后补理由。

## 20.1 通用 REST Connector 配置契约

PatWiki 提供 `rest_json` / `generic_json` 类型的配置驱动 Connector，用于接入没有专用 SDK 的供应商。配置只描述 HTTP 请求和响应映射，不能包含 API Key、Cookie、OAuth token 或其他明文凭证。凭证通过 `ConnectorCredential.credential_ref` 引用系统凭证存储：开发测试可使用 `env://VARIABLE_NAME`，正式环境使用 `keyring://service/account`。

最小配置结构如下：

```json
{
  "auth": {
    "type": "api_key",
    "header": "X-API-Key",
    "required": true
  },
  "retry": {
    "max_attempts": 3,
    "backoff_seconds": 0.5,
    "max_delay_seconds": 30
  },
  "search": {
    "method": "GET",
    "path": "/patents/search",
    "params": {
      "q": "{{query.expression}}",
      "applicant": "{{query.applicant}}",
      "cursor": "{{cursor}}",
      "limit": "{{limit}}"
    },
    "response": {
      "records_path": "results",
      "next_cursor_path": "meta.next_cursor",
      "watermark_path": "meta.updated_at",
      "source_version_path": "meta.version"
    }
  },
  "record": {
    "external_record_id": "id",
    "identifiers": [
      {
        "identifier_type": "publication",
        "raw_value_path": "publication.number",
        "jurisdiction_code_path": "publication.country"
      }
    ],
    "fields": {
      "publication_number": "publication.number",
      "title": "title",
      "applicant": "applicant.name",
      "publication_date": "publication.date"
    },
    "legal_events": {
      "path": "legal_events",
      "provider_event_id_path": "id",
      "event_code_path": "code",
      "event_date_path": "date",
      "status_path": "status"
    }
  }
}
```

模板变量只允许来自标准查询、游标、分页大小和单件身份：`query.*`、`cursor`、`limit`、`identifier.*`。响应路径使用点号和数组下标，例如 `results[0].publication.number`。Connector 只返回 `ProviderPatentRecord` / `SearchPage`，随后必须继续经过快照、身份解析、观察、审查和统一应用链路。

HTTP 语义必须保持一致：`429` 优先遵守 `Retry-After`，超时、连接错误和 `408/425/5xx` 属于可重试错误，`401/403` 和参数错误属于永久错误。错误消息、快照和日志不得包含认证头或敏感请求值。endpoint 只允许 `http/https`，请求路径不得跳转到未配置主机。

REST Connector 必须设置有限的 `timeout_seconds`（默认 30 秒），禁止无限等待；HTTP 客户端不自动跟随重定向，供应商返回 3xx 时作为配置错误处理。`config_json` 不得保存 API Key、Cookie、OAuth token 或密码，必须只保存 `credential_ref`。

## 20.2 MCP 只读 Adapter 规则

MCP 接入只能提供固定语义工具，例如 `search_patents`、`get_patent`、`get_legal_events` 和健康检查。`McpReadonlyConnector` 必须把工具结果映射为统一 `ProviderPatentRecord`，再进入同一同步管道。禁止增加任意 SQL、任意资源路径、任意表/字段读取、绕过观察审查的写工具；MCP 返回的错误也必须转为 Connector 的标准错误语义。

## 22. 首个 MVP 决策

首个 Provider-neutral MVP 固定包含：

- 一个模拟 Connector 和一个真实 Connector；
- 手动刷新单件专利；
- 定时执行一个申请人或检索式订阅；
- 法律状态事件时间线和当前状态投影；
- 外部事实冲突审查；
- 原始快照、游标、幂等、失败重试和重放；
- 同步运行列表、订阅状态和专利最近同步信息。

MVP 不以“成功调用过供应商 API”为完成。只有在重复执行不重复、故障可恢复、用户字段不覆盖、身份不误合并、每个正式变化可追溯到原始响应时，才能判定完成。
