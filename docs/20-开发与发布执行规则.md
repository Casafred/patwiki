# PatWiki 开发与发布执行规则

> 状态：强制执行
> 更新日期：2026-09-22

## 1. 目的

本规则统一 PatWiki 的开发验证、Git 提交、GitHub Actions 构建和安装包交付方式，避免本机环境差异、磁盘空间不足、原生依赖差异或未提交文件导致安装包与源码不一致。

本项目的安装包以 GitHub 云端构建结果为唯一交付来源。开发者或 Agent 不得在本机生成、验证或分发 Windows 安装包。

## 2. 强制发布链路

所有功能修改必须按以下顺序执行：

1. 在本机完成代码检查和自动化测试。
2. 检查工作区，确认只包含本次任务相关文件，不提交用户已有的无关修改、密钥、数据库、上传文件或构建产物。
3. 提交到当前 `main` 分支并推送到远端 `origin/main`。
4. 由 `.github/workflows/build.yml` 在 GitHub Actions 的 Windows runner 上构建。
5. 从对应 GitHub Actions run 下载 `patwiki-windows-msi` 或 `patwiki-windows-nsis` Artifact，作为测试和交付安装包。
6. 构建失败时修复源码后重新提交并推送；不得通过本机打包绕过云端构建失败。

`main` 是可触发正式 Windows 构建的唯一分支。提交到其他分支不会被视为可交付安装包来源。

## 3. 本机允许执行的操作

本机只用于开发和质量验证，可以执行：

- Python 单元测试、迁移检查、`compileall`、静态检查和只读发布检查；
- 前端 `lint`、TypeScript 检查和 Vite 构建；
- Rust `cargo check` 或其他不生成安装包的编译检查；
- 本地开发服务器、后端开发模式和功能联调；
- `git diff`、`git diff --check`、工作区审计和测试数据检查。

本机不得执行以下操作：

- `python -m PyInstaller` 生成后端发布目录；
- `scripts/build_windows.ps1`；
- `tauri build`、`npm exec ... tauri build` 或任何 MSI/NSIS/EXE 安装包构建命令；
- 使用本机生成的 `dist`、`target`、MSI、NSIS EXE 或其他发布产物进行交付或验收。

`scripts/build_windows.ps1` 已实现 CI-only 保护。本机调用必须直接失败；不得通过伪造环境变量、修改脚本或临时复制脚本绕过该保护。

## 4. GitHub Actions 构建职责

`.github/workflows/build.yml` 负责在干净的 Windows runner 上：

- 安装锁定的 Python、Node.js 和 Rust 工具链；
- 安装后端依赖并执行 PyInstaller；
- 安装前端锁定依赖并执行生产构建；
- 准备 Tauri Windows 打包工具；
- 构建 MSI 和 NSIS 安装包；
- 校验 MSI/NSIS 文件确实生成并上传 Artifact。

构建脚本必须检查 `GITHUB_ACTIONS=true` 且 `GITHUB_REF_NAME=main`。任何新增发布方式都必须保留相同的云端构建边界，并同步更新本规则和工作流文档。

## 5. 修改后的最低验证门禁

根据变更范围执行对应检查：

- 后端：相关测试、完整测试（适用时）、`python -m compileall app`；
- 语义检索：`scripts/semantic_release_check.py` 及语义专项测试；
- 前端：`npm run lint`、`npx tsc -b`、`npm run build`；
- Tauri：`cargo check` 和 `cargo fmt --check`（环境具备 `rustfmt` 时）；
- 所有修改：`git diff --check`、敏感信息检查、迁移/启动检查（适用时）。

本机验证通过不等于发布完成。发布完成的判定还必须包含：提交已推送到 `origin/main`，GitHub Actions 构建成功，且 MSI/NSIS Artifact 可下载。

## 6. 提交与工作区规则

- 提交前必须查看 `git status --short` 和变更摘要。
- 用户已有或来源不明的修改必须保留，不得覆盖、回退或顺手格式化。
- 与当前任务无关的修改不得混入提交；如果相关文件同时包含用户修改，必须逐段审阅后再决定是否提交。
- 不得提交本地数据库、运行时数据、密钥、上传文件、依赖缓存或构建产物。
- 功能代码、测试、文档和构建配置应在提交信息中清楚说明；推送后必须检查对应 Actions run，而不是只报告“已推送”。

## 7. 失败处理与回滚

GitHub Actions 失败时，先根据日志定位失败阶段：依赖安装、测试、PyInstaller、前端构建、Tauri 工具准备、MSI/NSIS 打包或 Artifact 上传。修复后重新运行本机允许的验证，再提交推送。

云端生成的安装包只作为该次 commit 的构建产物使用。发现发布回归时，应修复源码并重新构建，或回滚到已验证的 commit；不得用另一份本机安装包替代当前 commit 的云端 Artifact。

## 8. Agent 执行要求

任何 Agent 在修改代码前必须阅读本规则。涉及语义检索、MCP、外部专利同步、导入、打包或桌面端的任务，还必须阅读 `AGENT_GUIDE.md` 指向的专项架构文档。

Agent 必须在中间状态明确说明：本机仅执行验证，安装包将在推送 `main` 后由 Actions 构建。除非用户明确改变本规则，否则不得自行启动本机安装包构建。
