# PatWiki 部门协同共享与文件同步架构设计文档

> 文档状态：架构基线，供后续开发执行
> 文档版本：v1.0
> 编写日期：2026-09-26
> 适用范围：部门领导、开发维护管理员、撰写组、检索组、分析组之间的数据权限、责任品类、文件交换、离线同步及未来局域网/中继服务器协作
> 关联文档：`15-专利全局索引与表格检索契约.md`、`16-外部专利数据同步与监控架构规范.md`、`04-专利业务模型设计.md`

## 1. 文档目的

本文档将部门协同需求转化为可以分阶段实现的系统设计，解决以下问题：

1. 部门领导和开发维护管理员可以掌握全部数据，并拥有最高管理权限。
2. 撰写组、检索组、分析组可以按组、组长、具体同事和负责品类划分数据范围。
3. 同一品类下的撰写、检索、分析人员自动形成协作关系。
4. 在没有服务器互通的前提下，通过加密同步文件完成全量或指定数据交换。
5. 共享数据默认只读；经身份、授权和编辑密码确认后，才允许形成可审查的编辑变更。
6. 所有导出、导入、授权、冲突处理和数据变更都可追溯。
7. 第一阶段的文件协议可以直接演进为未来中继服务器、局域网和实时协作的传输协议。

本文不把普通 Excel 导出当作协同同步。Excel/CSV/Word 是面向阅读或业务交付的工作文件；协同同步必须保留全局实体 ID、版本、权限、来源、删除标记和冲突信息。

## 2. 结论摘要

### 2.1 推荐的总体方向

采用“本地优先 + 统一同步协议 + 可替换传输层”的三层架构：

```text
┌──────────────────────────────────────────────────────────────┐
│                    PatWiki 本地客户端                         │
│  React/Tauri UI · FastAPI · SQLite · 附件文件存储              │
│                                                              │
│  权限计算器  业务数据服务  协同同步引擎  包导入导出  审计日志   │
└───────────────────────┬──────────────────────────────────────┘
                        │ 统一 Sync Envelope / Package 协议
           ┌────────────┴─────────────┐
           │                          │
    第一阶段：文件传输             第二阶段：局域网/中继传输
    网盘、U 盘、手工发送            HTTP/WebSocket/内网共享目录
           │                          │
    .pwshare 加密包                  Relay Server / LAN Node
```

第一阶段不复制或替换整个 SQLite 文件，也不让接收方直接覆盖本地数据库。同步包只包含经过授权的数据变更或快照，由本地同步引擎校验、预览、冲突处理后，在事务中写入本地数据库。

### 2.2 必须先修正的现状

当前代码可以复用的基础：

| 现有能力 | 位置 | 可复用方式 |
|---|---|---|
| 本地 SQLite、版本化迁移和迁移前备份 | `backend/app/database.py`、`migration_service.py` | 新模型必须接入现有迁移服务 |
| 全局 Patent 实体和 `PatentIdentifier` | `models/patent.py`、`models/identity.py` | 同步必须使用稳定实体 ID和专利标识，不按本机自增 ID 合并 |
| 多数据库投影 | `PatentDatabaseMembership`、`DatabaseMembership` | 作为业务库范围和访问范围的一层约束 |
| 用户、部门、组、产品线字段 | `models/user.py`、`models/organization.py` | 作为迁移兼容入口，后续扩展为多对多关系 |
| 专利字段修改历史 | `PatentHistory` | 同步应用必须同事务写入历史 |
| 附件元数据、外置二进制 | `Attachment` | 包中使用内容哈希和附件清单，不直接序列化数据库路径 |
| 外部专利源同步 | `models/sync.py`、`api/sync.py` | 继续只服务外部 Provider，不与部门协同同步混用 |
| 库成员 Owner/Editor/Viewer | `DatabaseMembership` | 保留为数据库级权限，新增更细的数据范围和同步授权 |

当前缺口：

| 缺口 | 影响 | 处理要求 |
|---|---|---|
| 当前用户无真正登录鉴权，主要靠 localStorage 选择用户 | `admin`、领导、成员身份不能作为安全边界 | 第一阶段必须增加本地身份校验；进入生产前必须接入公司身份或设备身份 |
| 用户只能挂一个 `group_id` 和一个 `product_line_id` | 无法表达一个同事负责多个品类或跨组协作 | 新增多对多责任关系，旧字段仅作为兼容投影 |
| `DatabaseMembership` 只有 owner/editor/viewer | 无法表达组长、品类范围、字段权限、同步权限 | 保留库角色，新增授权策略和数据范围 |
| 部门/组使用 `Department` 自关联表达，语义混合 | 组层级和组织部门难以审计 | 引入组织单元类型和显式组模型，迁移期间兼容旧结构 |
| 外部同步模块面向供应商 API/MCP | 与同事之间的同步语义不同 | 新建 `collaboration_sync` 子系统，不复用 `ConnectorDefinition` 作为同事同步连接器 |
| 现有备份主要用于迁移回滚 | 没有同步包收件箱、发件箱、隔离区 | 增加同步工作区目录和包登记表 |
| 没有字段级授权与协同变更冲突模型 | 接收后无法安全判断哪些字段可覆盖 | 增加字段策略、变更包、冲突和授权模型 |

## 3. 设计原则与边界

### 3.1 原则

1. **全局实体稳定**：所有跨电脑交换的数据必须有跨设备稳定的 `entity_uid`；本地自增整数只用于本机查询。
2. **默认最小权限**：共享包默认只读，导入只产生候选或快照，编辑必须通过显式授权。
3. **同步不等于覆盖**：同步包只提交事实和变更，接收端先校验、预览、审查，再应用。
4. **按字段处理冲突**：不能以整行或整表最后写入覆盖所有人的工作。
5. **来源和历史不可丢失**：导出者、导入者、包版本、原值、新值、审批者和时间必须保留。
6. **文件协议与传输解耦**：网盘、局域网、中继服务器只负责搬运包，不改变包内业务语义。
7. **外部事实与内部判断分离**：官方专利事实、内部分类、风险结论、备注、评论和 AI 建议使用不同的所有权和冲突规则。
8. **离线可用**：断网时本地查询、编辑、导出和生成同步包仍可用。
9. **可回滚**：每次同步应用前自动创建本地数据库备份和可逆的同步事务记录。

离线文件一旦被复制、解密或导入到接收方设备，发送方无法即时撤回已经交付的内容。因此“撤销共享”只能阻止未处理包继续导入或解锁，不能保证已被读取、截图、复制或再次导出的内容消失；必须结合有效期、接收范围、字段脱敏、加密、审计和后续撤销标记降低风险。

### 3.2 非目标

第一阶段不包含：

- 自动把多个同事的 SQLite 文件直接合并；
- 通过共享目录让多个程序同时打开同一个 SQLite 文件；
- 首期建设云端主数据中心或完整实时协同编辑；
- 用密码替代所有身份认证和审计；
- 自动覆盖人工风险判断、分类、项目关系或备注；
- 同步 API/MCP 凭证、向量索引、任务租约、机器路径和本地缓存；
- 把普通 Excel 导入当作具有版本和权限语义的同步。

## 4. 组织、角色与责任品类模型

### 4.1 组织层级

```text
公司
└── 专利部门
    ├── 部门领导 1
    ├── 部门领导 2
    ├── 开发维护管理员（系统管理员，可多人）
    ├── 撰写组
    │   ├── 组长 A
    │   └── 同事 A1、A2 ...
    ├── 检索组
    │   ├── 组长 B
    │   └── 同事 B1、B2 ...
    └── 分析组
        ├── 组长 C
        └── 同事 C1、C2 ...
```

组织模型必须允许：

- 一个用户同时负责多个品类；
- 一个用户参与多个协作组或临时项目；
- 一个品类对应多个撰写、检索、分析成员；
- 用户职责变化后保留历史，不改变既有同步包的原始授权记录；
- 组长继承本组范围，但不自动获得其他组的编辑权；
- 部门领导和系统管理员拥有部门内全部数据的管理权。

### 4.2 角色定义

角色是权限上限，数据范围另由责任品类、业务库和同步授权共同决定。

| 角色代码 | 中文 | 数据范围 | 默认能力 |
|---|---|---|---|
| `system_admin` | 开发维护管理员 | 全系统、全部业务库 | 用户/组织/权限/迁移/备份/同步策略/全部数据读写 |
| `department_leader` | 部门领导 | 部门全部数据 | 查看、编辑、审批、授权、导出、撤销共享；不能绕过审计 |
| `group_leader` | 组长 | 本组负责的品类和被授权协作数据 | 查看、编辑、审核本组数据；可发起组内同步；可批准成员编辑 |
| `member` | 具体同事 | 本人负责品类和显式共享数据 | 查看、按授权编辑、生成指定范围同步包 |
| `viewer` | 只读协作人 | 被授予的记录/字段 | 查看和导出允许导出的内容，不得修改源数据 |

`system_admin` 和 `department_leader` 都属于最高权限，但职责不同：系统管理员负责系统和安全运维，部门领导负责业务数据和组织授权。两类角色的操作均需记录审计。

### 4.3 责任品类

不能继续只使用 `User.product_line_id` 表达责任范围。建议增加：

```text
User
  └── UserResponsibility
        ├── scope_type: product_line / product / category
        ├── scope_id
        ├── team_type: writing / retrieval / analysis
        ├── responsibility_level: owner / backup / reviewer
        ├── can_edit
        ├── valid_from / valid_to
        └── assigned_by / assigned_at
```

责任关系的唯一性约束建议为：

```text
(user_id, scope_type, scope_id, team_type, valid_from) UNIQUE
```

品类应优先关联现有 `Product` 和 `ProductLine`，如实际业务使用“类别/产品类型”而不是现有产品实体，则增加 `ProductCategory` 作为稳定字典，并用映射表连接产品线和类别。不要把品类名称写死在同步逻辑中。

### 4.4 自动协作关系

同一责任品类下，撰写、检索、分析三类责任人自动形成协作关系：

```text
CollaborationEdge
  source_user_id
  target_user_id
  scope_type / scope_id
  relation_type: same_category / reviewer / temporary
  default_access: viewer
  can_request_edit
  valid_from / valid_to
```

自动关系只提供“可发现和可申请”的基础，不直接给予跨组编辑权。默认规则：

- 同品类跨组成员：可看到已共享的记录，默认只读；
- 组长：可查看和处理本组范围；
- 跨组编辑：需要记录级或字段级显式授权，或者通过编辑密码解锁的同步变更能力；
- 部门领导/系统管理员：不受品类范围限制。

### 4.5 有效权限计算

对用户 `U`、记录 `R`、字段 `F` 和操作 `A`，权限计算顺序如下：

```text
1. 用户是否 active，设备是否已注册，当前会话是否有效？
2. system_admin 或 department_leader？是则进入全局范围，但仍检查字段保密级别和审计策略。
3. R 是否属于 U 可访问的 PatentDatabase？否 -> 拒绝。
4. R 的产品/品类是否命中 U 的责任关系、组长继承关系或显式共享授权？否 -> 拒绝。
5. F 的敏感级别和操作 A 是否被角色/字段策略允许？否 -> 拒绝。
6. 若数据来自共享包，包权限是否为 viewer？是且 A 为写入 -> 拒绝。
7. 若 A 为 apply/edit，是否存在 editor grant、审批记录或编辑密码解锁？否 -> 拒绝。
8. 写入时记录 actor、权限来源、包 ID、授权 ID和审计事件。
```

权限服务必须返回可解释结果，例如：

```json
{
  "allowed": false,
  "action": "edit",
  "reason_code": "shared_snapshot_read_only",
  "reason": "该数据包当前仅有阅读许可",
  "matched_scope": "product:42",
  "required_grant": "editor"
}
```

## 5. 数据分类、存储与同步策略

### 5.1 数据分类总表

| 数据类别 | 典型内容 | 本地权威存储 | 默认是否同步 | 传递方式 | 冲突策略 |
|---|---|---|---|---|---|
| 全局专利身份 | 申请号、公开号、授权号、法域、同族标识 | `Patent`、`PatentIdentifier` | 是 | 结构化记录 | 标识精确匹配；歧义进入冲突，不自动合并 |
| 官方专利事实 | 标题、摘要、申请人、日期、法律事件 | `Patent`、`LegalStatusEvent`、来源观察 | 可选 | 快照/变更记录 | 外部权威来源优先；人工字段不得静默覆盖 |
| 内部业务标注 | 分类、模块、风险、备注、范围结论 | `Patent`、`custom_fields` | 按字段策略 | 字段级 delta | 三方合并，人工值冲突待审查 |
| 自定义字段定义 | 字段类型、选项、公式、关联配置 | `CustomField`、字段治理表 | 管理员/领导可同步 | schema + definition | 版本兼容检查；定义冲突禁止自动覆盖 |
| 产品/品类责任 | 产品、责任人、组、协作关系 | 组织与责任模型 | 仅授权管理员包 | control plane 数据 | 管理员审批后应用 |
| 业务库/视图 | `PatentDatabase`、`PatentView`、筛选和列配置 | 现有库和视图模型 | 可选 | 配置快照 | 以库 UID/视图 UID 合并，删除采用 tombstone |
| 关系数据 | 同族、引用、项目、标签、跨表链接 | 关系表 | 是 | 独立关系记录 | 关系集合并集；解除关系需显式 tombstone |
| 评论与讨论 | 评论、回复、@提及、解决状态 | `Comment` | 是 | 追加式事件 | 评论追加合并，解决状态按权限和时间审查 |
| 修改历史和审计 | `PatentHistory`、同步审计、导入记录 | 本地数据库 | 只同步必要来源记录 | 追加式日志 | 不覆盖、不删除；合并去重 |
| 附件 | PDF、图片、交底书、证书 | 文件系统 + `Attachment` 元数据 | 按选择/大小策略 | 内容寻址 blob | SHA-256 去重；同名不同哈希并存 |
| AI 结果和向量 | AI 字段、embedding、索引状态 | `AIFieldValue`、本地索引 | 默认不传向量；AI值按策略传 | 结构化值，可选提示来源 | AI 值标识模型版本；向量在本地重建 |
| 外部同步运行状态 | connector、cursor、lease、provider credential | `models/sync.py` | 禁止普通协作同步 | 不进入 `.pwshare` | 每台设备独立维护 |
| 本机 UI 状态 | 窗口、缓存、搜索历史 | localStorage/本地配置 | 禁止 | 不传递 | 无 |

### 5.2 三种同步内容

第一阶段必须区分以下三种内容，不能只提供一个“导出全部”按钮：

1. **完整快照 `snapshot`**：选定业务库、视图、品类或记录在某一时刻的完整可读数据，适合首次共享和灾备。
2. **增量变更 `delta`**：基于同步检查点导出新增、修改、删除标记，适合日常交换，文件小且可重复导入。
3. **控制面 `control`**：组织、用户责任、字段定义、权限和同步策略，只允许系统管理员/部门领导导出和导入。

“当前全部数据”应当是一个可配置的快照范围，而不是直接把本机所有表打包。默认不包含本机外部连接器凭证、同步游标、向量库、缓存和未授权数据库。

### 5.3 跨品类专利的隔离规则

同一专利可能同时属于多个产品或品类，但共享专利主记录不等于共享该专利的全部内部信息。权限计算必须对每个字段和数据类别分别执行：

- 专利身份、公开事实等公共字段，按接收者对相应记录的最小可见范围导出；
- 品类归属、责任关系、检索式、撰写状态、风险判断、内部备注、分析结论和项目关系，必须带有品类或数据类别范围，并按该范围单独授权；
- 同一专利属于多个品类时，只能导出接收者已获授权的品类投影，不能因为命中一个品类就暴露其他品类的内部字段；
- 包内应记录字段的 `scope`、`owner_scope` 和脱敏状态；未授权字段应省略或输出不可逆的脱敏占位符，不得依赖前端隐藏；
- 导入时继续按字段范围校验，禁止用完整主记录覆盖本地其他品类的字段或关系。

因此，导出预览和导入预览都必须按“记录 + 品类/数据类别 + 字段”展示范围，审计中保存实际发送和应用的字段集合。

## 6. 第一阶段文件同步架构

### 6.1 本地同步工作区

建议在现有 `DATA_DIR` 下增加：

```text
data/
├── patwiki.db
├── attachments/
├── backups/
└── collaboration_sync/
    ├── inbox/          # 用户选择导入但尚未应用的文件
    ├── outbox/         # 已生成、待发送的文件
    ├── archive/        # 已处理包及处理结果
    ├── quarantine/     # 签名、哈希、格式或权限校验失败的包
    ├── snapshots/      # 本地自动生成的同步前快照
    ├── manifests/      # 已知包清单和索引
    └── keys/           # 设备密钥、用户公钥和本地密钥引用
```

目录中的文件名不能直接作为业务身份。所有文件通过 `package_id`、内容哈希和数据库登记表识别。

### 6.2 同步包格式

文件扩展名：`.pwshare`。本质是 ZIP 容器，但必须先验证清单和签名，再解压到隔离目录。

```text
package.pwshare
├── manifest.json
├── schema.json
├── permissions.json
├── data/
│   ├── patents.ndjson
│   ├── patent_identifiers.ndjson
│   ├── fields.ndjson
│   ├── field_definitions.ndjson
│   ├── databases.ndjson
│   ├── views.ndjson
│   ├── relations.ndjson
│   ├── comments.ndjson
│   ├── history.ndjson

```

NDJSON 用于大文件流式处理，避免一次性把全部数据加载到内存。每条数据都应包含：

```json
{
  "entity_type": "patent",
  "entity_uid": "pat_01J...",
  "record_version": 17,
  "updated_at": "2026-09-26T10:30:00Z",
  "updated_by": "user:alice",
  "scope": {"database_uid": "db_...", "product_ids": [42]},
  "payload": {"title": "...", "custom_fields": {}},
  "field_provenance": {},
  "source_package_id": "pkg_..."
}
```

### 6.4 稳定 ID、版本和删除

现有整数主键不能单独承担跨设备同步身份。建议为可同步实体增加：

```text
entity_uid       全局唯一、创建后不变，推荐 UUIDv7 或带前缀的 UUID
origin_node_uid  首次创建实体的设备
record_version   本实体的单调版本，仅在本地事务中递增
updated_at       UTC 时间
updated_by       用户 UID 或系统 actor UID
deleted_at       软删除时间，空表示存在
```

删除不能物理消失。删除会生成 `tombstones.ndjson`，至少保留到所有活跃同步通道确认，默认保留 180 天。恢复删除也是一条新的变更，不直接删除 tombstone。

## 7. 第一阶段用户操作流程

### 7.1 生成共享文件

1. 用户打开“部门协同 / 数据同步”。
2. 选择同步类型：全部数据、当前库、指定视图、指定品类、指定记录、从上次检查点开始。
3. 选择数据类别：专利事实、内部标注、关系、评论、附件、字段定义、责任配置。
4. 系统按当前用户权限过滤可导出范围，显示预计记录数、敏感字段和附件大小。
5. 选择接收方或协作通道。默认接收权限为 `viewer`。
6. 选择是否允许编辑；若允许，必须设置编辑授权对象和编辑密码，并填写有效期。
7. 系统生成包、计算哈希、签名、写入发件箱，并记录 `SyncPackage`。
8. 用户将 `.pwshare` 上传公司网盘或通过其他批准方式传给同事。

导出预览必须显示：

- 数据范围和记录数量；
- 包含/排除的字段；
- 是否包含附件；
- 是否包含评论和历史；
- 接收者默认权限；
- 是否存在脱敏字段；
- 包大小和加密状态。

### 7.2 接收和预览

1. 用户在“收件箱”选择 `.pwshare`。
2. 系统先把文件复制到 `quarantine/`，验证扩展名、ZIP 路径、大小、恶意路径、清单、哈希和签名。
3. 通过基础校验后解析 manifest，但不立即写入业务表。
4. 校验发送者是否在允许的部门、组、协作通道或临时授权范围。
5. 展示新增、修改、删除、附件、权限和冲突预览。
6. 用户选择：作为只读快照查看、导入为候选、逐项应用、全部接受（仅限高权限用户）。
7. 应用前自动创建本地同步前备份。
8. 在一个事务或可恢复批次中写入结果；失败时恢复本地备份并保留失败包。
9. 完成后将包移动到 `archive/`，登记应用结果和检查点。

### 7.3 只读共享和编辑授权

导入共享包后默认产生以下状态：

```text
SharedSnapshot.status = imported
SharedSnapshot.access = viewer
SharedSnapshot.source_package_id = pkg_...
```

只读用户可以查询、筛选、查看允许导出的内容和生成阅读性工作文件，但不能直接修改共享数据。

编辑有两种方式：

1. **显式授权**：发送者或部门领导把接收者加入 `editor_grants`，指定记录/字段、有效期、可执行动作。
2. **编辑密码解锁**：包创建者生成临时编辑能力，接收者输入密码后只获得该包声明范围内的编辑能力。密码只作为能力证明，不能提升用户的全局角色。

编辑解锁后，接收方仍然只修改本地工作副本，并生成 `delta` 变更包。原始共享快照保持不变，发送回源方后由源方或有审批权的人审查合并。

编辑授权必须具备：`grant_id`、授权人、被授权人或接收者标识、数据范围、字段范围、动作、创建时间、过期时间、撤销状态和审计记录。

## 8. 合并、冲突与字段所有权

### 8.1 三方比较

对每个实体/字段，使用：

```text
base   导出方和接收方共同确认的上一个检查点值
local  接收方本地当前值
remote 包内发送方的新值
```

合并规则：

| 情形 | 结果 |
|---|---|
| `local == base`，`remote != base` | 可应用 remote |
| `local != base`，`remote == base` | 保留 local |
| `local == remote` | 标记已同步，不重复写历史 |
| local 和 remote 都不同于 base | 生成冲突，不自动覆盖 |
| identity 标识冲突 | 整条记录进入 identity conflict |

### 8.2 字段所有权

| 所有权 | 示例 | 默认规则 |
|---|---|---|
| `external_authority` | 官方号码、公开日、授权日、法律事件 | 依据来源和审查策略更新 |
| `department_master` | 部门统一分类、正式风险结论、主表规范字段 | 部门领导/授权组长审批 |
| `team_owned` | 本组负责的检索式、撰写状态、分析结论 | 责任组成员编辑，跨组默认只读 |
| `user_owned` | 个人草稿、个人备注 | 只由创建者或显式授权人修改 |
| `shared_collaboration` | 评论、协作标签、任务状态 | 追加式或字段级权限 |
| `ai_suggestion` | AI 摘要、分类建议、风险建议 | 只作为建议，保留模型和版本 |

第一阶段不得把所有字段设置成简单的“最后写入覆盖”。

### 8.3 冲突处理界面

冲突页面至少显示：字段名、中文名称、base/local/remote 三个值、来源人、来源包、时间、字段所有权、建议动作。动作包括：

- 接受远端；
- 保留本地；
- 手工合并；
- 标记为部门标准值；
- 忽略本次变更；
- 创建后续修正包。

所有冲突决策写入 `SyncConflict`，不能只修改最终字段而丢失决策。

## 9. 安全设计

### 9.1 身份与设备

第一阶段至少实现本地身份边界：

- 首次启动创建或绑定本机用户；
- 设备生成 `node_uid` 和 Ed25519 密钥对；
- 用户登录使用本地 PIN/Windows 凭据或公司身份；
- 当前用户切换必须经过身份验证，不能只改 localStorage；
- 管理员操作要求重新认证；
- 用户停用后不能导出新包或应用编辑包；
- 保留设备撤销列表。

在没有上述身份边界之前，只能称为开发/演示功能，不得把 `role=admin` 当作生产安全控制。

### 9.2 加密和签名

推荐默认策略：

- 包体使用 AES-256-GCM 加密；
- 每个包随机生成内容密钥；
- 内容密钥通过接收者公钥或临时编辑密码封装；
- 密码派生使用 Argon2id，不能保存明文密码；
- 包使用发送设备 Ed25519 私钥签名；
- 接收端验证签名者、签名时间、密钥撤销状态和根哈希；
- 密钥只保存引用或操作系统安全存储，不写入普通业务表；
- 敏感字段可在包内单独加密，未授权用户看到脱敏占位符。

如果第一阶段因部署条件不能立即完成公钥分发，仍必须先实现：强随机包密钥、AES-GCM、Argon2id 密码验证、完整性哈希、密码失败锁定和审计；上线前补齐签名和设备信任。

### 9.3 包安全校验

导入前必须拒绝：

- ZIP 路径穿越和绝对路径；
- 解压炸弹、单文件超限、总大小超限；
- manifest 与实际文件哈希不一致；
- 未知格式版本或必需字段缺失；
- 签名不可信、签名者已撤销或包已过期；
- 包声明范围超出发送者权限；
- 重复 `package_id` 已成功应用；
- 目标数据库、字段定义或实体版本不兼容。

## 12. 前端功能规划

新增设置区域“部门协同与数据同步”，建议拆分为：

UI 状态必须明确区分：

- 本地可编辑数据；
- 共享只读快照；
- 已解锁但尚未提交的本地工作副本；
- 待审查的远端变更；
- 冲突数据；
- 已应用且可追溯的数据。

## 13. 第一阶段实施路线图

- 实现冲突审查页面和批量决策；
- 实现接收方编辑后生成回传 delta；
- 将同步应用结果写入 `PatentHistory`、附件来源和审计。

验收：两台设备并行修改同一字段时生成冲突，不会静默覆盖；评论、关系和附件可幂等合并。

### P4：签名、运维和发布（1 周）

- 接入设备密钥和 Ed25519 签名；
- 增加密钥撤销、包过期和失败锁定；
- 增加同步状态诊断、重建和清理任务；
- 增加管理员备份恢复、数据保留和审计导出；
- 完成 Windows 安装包和离线场景验收。

## 14. 测试与验收门禁

### 14.1 权限测试

- 两名部门领导和多个系统管理员都能访问全部业务库；
- 组长只能管理本组责任范围，除非有额外授权；
- 同品类跨组成员可以发现协作关系，但默认不能编辑；
- 一个成员负责多个品类时，权限范围是多个品类的并集；
- 责任关系过期后立即失去新增导出和编辑能力；
- 字段策略优先于一般库角色；
- 停用用户不能生成或应用包；
- 前端绕过按钮隐藏后直接调用 API 仍被拒绝。

### 14.2 包和同步测试

- 全量快照、指定记录、指定品类和 delta 都能生成；
- 空包、重复包、损坏包、错误版本包、错误签名包进入隔离区；
- ZIP 路径穿越、超限文件和恶意 manifest 被拒绝；
- 重复导入同一个 `package_id` 是幂等的；
- 同一附件内容不同文件名只保存一份 blob；
- 删除和恢复删除不会因包顺序错误而永久丢失；
- 中断导入后可恢复或回滚；
- 外部 Provider 的 connector、cursor、credential 不会出现在协同包中。

### 14.3 冲突测试

- local 未变化、remote 变化时可自动应用；
- remote 未变化、local 变化时保留本地；
- local/remote 同时变化时生成冲突；
- 关系、评论、历史、附件按照追加/集合规则合并；
- 字段定义和 schema 版本不兼容时阻止自动应用；
- 所有应用和冲突决策都能在历史和审计中追溯。

### 14.4 性能目标

第一阶段建议目标：

- 10 万条 NDJSON 记录导出不超过 2 分钟，内存不随总记录数线性增长；
- 10 万条记录包预览不超过 30 秒；
- 1 万条变更应用使用批量事务，不逐条提交；
- 包失败时不留下半应用数据；
- 附件大于配置阈值时明确提示并支持不带附件同步。

## 15. 数据迁移和兼容策略

1. 旧用户的 `role=admin` 根据管理员清单迁移为 `system_admin` 或 `department_leader`，不能自动把所有 admin 都当作系统管理员。
2. 旧 `department_id` 迁移为 `OrganizationUnit(unit_type=department)`。
3. 旧 `group_id` 迁移为 `OrganizationUnit(unit_type=team)`，根据名称或人工配置补充 `team_type`。
4. 旧 `product_line_id` 迁移为一条 `UserResponsibility`，后续允许增加多条。
5. 为现有 Patent、Database、View、Attachment、Comment、History 生成稳定 UID。
6. 旧库的 owner/editor/viewer 继续生效，但同步权限需要重新经过 `PermissionService` 计算。
7. 现有外部同步表和 API 保持兼容；部门协同 API 使用独立前缀和独立模型。
8. 任何迁移都遵守现有“迁移前备份、版本记录、失败恢复”流程。

## 16. 未来中继服务器和局域网演进

### 16.1 不改变第一阶段包协议

未来服务器不是重新发明一套数据格式，而是转发和登记同一套 `Sync Envelope`：

```text
本地客户端
  ├── outbox change
  ├── HTTP/WebSocket 上传 Sync Envelope
  └── 接收 server ack / remote envelope

Relay Server
  ├── 身份认证和授权
  ├── channel membership
  ├── append-only change log
  ├── package/blob storage
  ├── conflict notification
  └── device checkpoint
```

服务器初期只做中继和权限检查，不直接解释所有业务字段。客户端仍保留本地 SQLite 和离线能力；当服务器稳定后，再把部门共享数据的权威投影迁移到 PostgreSQL 或其他服务端数据库。

### 16.2 服务器阶段新增能力

- 公司账号、SSO、MFA 和设备撤销；
- 中央组织、责任品类和权限策略；
- 每个协作通道的服务端检查点和变更日志；
- WebSocket/长轮询通知；
- 服务端附件对象存储和病毒扫描；
- 服务端冲突队列、审批和通知；
- 断线重连、幂等上传、断点续传；
- 管理员审计、保留策略和灾备。

### 16.3 局域网模式

局域网模式可以把一台受控电脑作为 Relay Node，使用 HTTPS 和局域网发现；不能让多个客户端直接访问同一个 SQLite 文件。局域网模式仍然以变更包/事件为单位，由各客户端本地应用。

### 16.4 实时协作边界

真正的实时协作需要把字段编辑、锁定、冲突和通知做成事件流。第一阶段的 `entity_uid`、`record_version`、`change_uid`、`checkpoint` 和 `tombstone` 必须从一开始保留，否则未来接入中继服务器时只能重写同步层。

## 17. 风险和决策记录

| 风险 | 等级 | 处理 |
|---|---|---|
| 没有真实身份认证却宣称有权限控制 | 高 | 先补本地身份，生产部署必须接入公司身份或设备认证 |
| 共享包包含未公开专利或商业秘密 | 高 | 默认加密、字段脱敏、包签名、收件人授权和审计 |
| 用整库替换导致本地工作丢失 | 高 | 禁止替换 SQLite，只允许事务化导入和本地备份 |
| 自增整数 ID 在不同电脑冲突 | 高 | 所有同步实体增加全局 UID |
| 复杂品类责任发生变化 | 中 | 多对多责任 + 有效期 + 历史，不把责任写死在用户表 |
| 多人同时修改同一字段 | 高 | 三方合并和显式冲突，禁止隐式 LWW |
| 附件太大导致网盘和导入失败 | 中 | 内容寻址、大小阈值、可选附件包和断点续传预留 |
| 外部同步和内部协同概念混用 | 高 | 独立模型、独立 API、独立服务和独立审计分类 |
| 未来服务器协议与本地包不兼容 | 中 | 第一阶段即固定版本化 manifest 和 envelope |

### ADR-001：不交换整个 SQLite 文件

原因：不同电脑的本地配置、缓存、权限、外部连接器、索引和自增 ID 不一致；直接覆盖会导致数据丢失和权限绕过。

### ADR-002：共享包默认只读

原因：接收方先获得信息知情权，编辑必须明确授权和审查；这与部门实际协作和敏感专利数据场景一致。

### ADR-003：同步包同时支持快照和增量

原因：首次共享需要快照，日常交换需要增量；只有一种格式会导致文件过大或无法恢复基线。

### ADR-004：文件协议与传输层解耦

原因：第一阶段依赖网盘/手工传递，未来可能切换局域网或中继服务器；统一包协议能降低迁移成本。
