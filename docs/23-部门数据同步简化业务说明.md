# PatWiki 部门数据同步简化业务说明

> 文档状态：业务规则说明
> 版本：v1.0
> 更新日期：2026-10-01
> 适用范围：部门管理员、普通同事、部门总库和个人业务库之间的离线文件同步
>
> 本文用于统一产品和开发理解。它描述的是“怎么工作”，不是具体页面或接口设计。
> 本文作为本次简化需求的业务基线。与 21、22 号文档不一致时，以本文的目标流程为准；旧文档保留用于了解现有实现。本文不代表这些功能已经实现。

## 1. 目标和基本判断

PatWiki 采用“每个人本地工作、部门定期汇总”的方式运行：

- 每位同事在自己的电脑上独立安装 PatWiki，建立自己的数据库、导入资料和做标注。
- 部门不要求所有电脑实时联网，也不要求把所有人的数据库放在同一个服务器上。
- 每周由各同事选择需要对外共享的业务库，导出一个数据文件。
- 部门管理员收集这些文件，合并到部门总库，审计冲突并形成新的部门总数据文件。
- 同事下载部门总数据文件，导入本机；部门总表中已更新的专利，只更新其个人库中对应的专利记录。
- 同事之间可以互相导入指定业务库，但他人写入的内容必须能被识别、追踪和单独处理。

核心原则只有四条：

1. **登录只证明是谁在使用这台电脑；同步时只做权限校验。**
2. **同步不覆盖整库，统一采用增量合并。**
3. **有冲突不静默覆盖，必须留下冲突审计记录。**
4. **总库和个人细分库是不同层级的数据，不能互相替换。**

## 2. 账号和权限：保持简单

### 2.1 账号由管理员预先建立

部门管理员集中维护一张账号清单，至少包含：

| 字段 | 含义 |
|---|---|
| 用户名 | 同事登录 PatWiki 使用的唯一名称 |
| 用户工号 | 部门内部的稳定身份标识 |
| 初始密码 | 管理员生成并通过内部渠道分发 |
| 姓名 | 展示和审计使用 |
| 状态 | 启用、停用 |
| 角色 | 部门管理员或普通成员 |

管理员集中建立账号，以“部门标识 + 工号”关联跨电脑身份，用户名用于登录，姓名用于展示。给同事分发本人账号的初始化配置和初始密码；同事安装后导入配置即可登录，不需要在每台电脑重新创建管理员、逐一建账号或配置信任设备。账号配置是一次性初始化或人员权限变更时使用的管理文件，不属于专利数据同步文件。

客户端保存密码校验值，不保存部门明文密码清单；普通成员不获得管理员密码或其他同事密码。密码可在本机修改，修改不随专利数据同步。账号停用和权限变更通过管理员配置更新生效，离线电脑在接收更新前不会自动获知变更。

### 2.2 只保留两类同步角色

- **部门管理员**：可以收集、合并、审计和发布部门总数据；可以处理所有同步包。
- **普通成员**：可以导出本人有权共享的数据库，也可以导入管理员或其他同事提供的数据。

登录成功后，同步根据当前账号和本机已配置权限判断本次操作，不再次输入账号密码。各操作分别校验：

1. 导出：是否有选中库的导出权限；
2. 导入：是否有目标库的导入权限；
3. 编辑：是否有目标库的编辑权限；
4. 汇总和发布：是否有部门管理员权限。

不再为普通同步流程增加 Token 链、设备签名、复杂的多级账号校验或重复的收件人认证。权限结果应直接显示为“允许”或“拒绝”，并记录原因。

### 2.3 数据库权限

权限以“账号 + 数据库 + 操作”为基本单位：

| 操作 | 说明 |
|---|---|
| 查看 | 可以在本机打开数据库和查看数据 |
| 导出 | 可以将所选数据库或库内数据生成同步文件 |
| 导入 | 可以把同步文件导入本机数据库的共享区或个人库 |
| 编辑 | 可以修改本人库，或按授权对他人库形成独立编辑记录 |
| 汇总 | 仅部门管理员可以把成员文件合并进部门总库 |

默认规则是：个人创建的数据库由本人拥有；管理员可以汇总部门数据；他人导入后默认是可查看和可审计的共享数据，是否允许直接编辑由目标数据库的编辑权限决定。

导入预览和确认是一次操作，不再要求另领“应用 Token”、独立编辑密码或逐包收件人授权。数据包声明的角色、编辑者和来源仅用于追踪，不能自行增加接收方权限。普通成员不得修改部门总表的已发布基线；修改建议在个人库或独立变更中提交。

## 3. 数据库分层

### 3.1 部门总库

部门总库由管理员维护，是部门每周发布的统一结果，包含：

- 部门确认后的专利主数据；
- 已审核的公共字段和部门统一标注；
- 来源、版本、更新时间和冲突处理结果；
- 可供成员回传的稳定专利标识。

部门总库不是某一位同事个人数据库的复制品，也不直接覆盖成员本机的全部数据。

### 3.2 同事个人库和细分库

每位同事可以建立多个个人数据库，例如撰写库、检索库、重点客户库。个人库可以包含：

- 本人负责的专利；
- 从部门总库导入的公共信息；
- 本人的分类、备注、风险判断和工作状态；
- 经授权从其他同事处导入的专利或标注。

个人库的细分字段由本人维护，但涉及部门统一字段的更新，应接受部门总库发布的结果。

### 3.3 共享库

同事之间可以选择一个特定库进行互相导入。共享库导入后，系统必须保留原数据库、原记录、导出人和导入时间。共享数据不因为导入而变成接收人的原始数据。

## 4. 同步文件和稳定标识

### 4.1 文件类型

只需要两种业务文件：

1. **成员同步文件**：普通成员从自己选择的一个或多个数据库导出，供管理员汇总或供其他同事导入。
2. **部门总库发布文件**：管理员完成每周汇总后生成，供成员更新本机数据。

默认流程是“勾选整库 → 生成文件”，文件包含所选库的可共享完整数据及必要的版本和来源信息。**整库是导出范围，增量是接收端的合并方式**：完整文件也只应用新增或实际变化的数据，不覆盖整库。

部门总库默认发布完整文件，让首次安装或漏同步几周的同事也能一次导入完整总表。后续可提供“仅导出变更”作为优化，由系统自动选择可用基线，不要求普通同事手工管理检查点。

### 4.2 每条记录必须有稳定 ID

同步不能依赖各台电脑的自增数据库 ID。每条专利、每个数据库和每个变更都要有跨电脑稳定的唯一标识：

- `patent_uid`：专利主记录的稳定 ID；
- `database_uid`：业务库的稳定 ID；
- `change_uid`：一次修改的稳定 ID；
- `base_version`：修改发生时记录的版本；
- `record_version`：当前记录版本。

申请号、公开号、授权号等号码用于辅助匹配和去重，但不能代替稳定 ID。号码冲突或一号对应多条记录时必须进入人工审计。

两位同事分别首次导入同一专利时，可能得到不同 UID。接收端先匹配 UID，再按标准化号码及法域匹配；匹配成功后保存 UID 映射，合并到同一专利，不因为 UID 不同而重复新增。同族的不同专利不得仅凭同族关系合并。

### 4.3 增量内容

成员同步文件至少包含：

- 文件和导出者信息；
- 导出数据库清单；
- 记录的新增、修改和删除标记；
- 每项修改的字段、原值、新值、修改人和修改时间；
- 导出时使用的版本或检查点；
- 来源数据库和来源记录。

增量文件可以重复导入。系统根据 `change_uid` 去重，不能因为用户重复下载或重复导入而重复写入。

只有增量模式需要同步检查点，检查点按来源库和接收对象分别记录。生成文件不代表对方已接收，不能立即丢弃未确认变更。缺少基线或遗漏中间版本时，要求补齐或导入完整文件。全量文件中未出现的记录不视为删除；省略字段不视为清空，清空必须是显式变更。

## 5. 每周部门汇总流程

### 5.1 成员导出

每位同事在本周截止前：

1. 登录自己的 PatWiki。
2. 选择需要对外同步的数据库，可以选择一个或多个整库。
3. 使用默认的整库导出；系统保留版本和变更信息。
4. 查看导出预览，确认数据库名称、记录数量和字段范围。
5. 生成同步文件并提交给部门管理员。

“选择整库”表示选择该业务库的全部可同步记录，不要求同事逐条挑选专利。若某些字段不允许对外共享，应由数据库权限或字段策略提前配置。

同事可以预先保存“每周共享哪些库”和“哪些专利或数据需要统一更新”的配置，例如重点库全部专利的法律状态。共享范围与更新范围分别保存，并随数据文件传递更新请求，管理员汇总时去重。

### 5.2 管理员接收和预审

管理员把成员文件放入汇总区后，依次执行：

1. 校验文件格式、文件完整性和当前接收账号的汇总权限。来源人和来源库用于审计，不要求接收电脑重复登录发送者账号。
2. 登记文件来源、导出时间、来源数据库和文件版本。
3. 先生成变更预览，不直接写入部门总库。
4. 按 `patent_uid` 匹配已有记录；无法匹配时再使用专利号码辅助匹配。
5. 将变更分为可自动合并、新增、删除、冲突和无法匹配五类。

### 5.3 增量合并规则

| 情况 | 处理方式 |
|---|---|
| UID 和规范化专利号码均未匹配 | 新增记录，并记录首次来源 |
| 成员值与基线一致 | 没有成员新变更，保留总库现值 |
| 总库值与基线一致、成员值已修改 | 自动合并成员变更 |
| 总库值与成员值一致 | 无需修改，记录来源和处理结果 |
| 成员与总库相对共同基线都修改了同一字段且结果不同 | 生成冲突，等待管理员决定 |
| 多名成员提交相同新值 | 合并为一个结果，保留全部来源 |
| 多名成员提交不同新值 | 生成冲突，不能按最后导入覆盖 |
| 成员提交删除 | 先区分退出个人库和删除部门记录；部门删除须管理员确认，有新修改则生成冲突 |
| 号码命中多个专利或已删除记录 | 阻止自动合并，进入人工匹配 |

管理员的冲突处理选项至少包括：

- 保留部门总库值；
- 接受某位成员的值；
- 手工编辑后形成新值；
- 暂不处理，保留待审状态。

每个决定都要保存原值、候选值、最终值、处理人、处理时间和处理理由。

判断依据是共同基线、总库当前值和成员提交值，不是“本周有没有改”或电脑时间。无法获得共同基线且双方已有不同值时，进入待审。不同库的同名字段只有语义和类型一致才合并；个人分类和备注按来源库分别保留。未处理冲突保留旧的部门已确认值，不阻塞其他无冲突记录发布。

### 5.4 汇总后统一更新专利数据

管理员先完成成员数据汇总，再根据提前配置的更新范围，集中更新需要更新的专利：

1. 合并成员提交的更新请求，按专利去重。
2. 通过已有专利数据更新能力获取法律状态、公开信息等更新。
3. 对外部返回结果进行字段比较，保留数据来源、查询时间和实际变化。
4. 更新部门公共字段；涉及人工标注或已有不同值时进入审计，不覆盖个人判断。
5. 查询失败的专利保留原数据，记录失败状态，成功部分正常进入发布结果。

这里要区分“成员数据汇总”和“外部专利信息更新”两个步骤。成员不需要各自重复执行本次统一更新。

### 5.5 发布部门总数据文件

管理员完成合并和冲突审计后：

1. 提交本周汇总批次。
2. 为部门总库生成新的版本号和检查点。
3. 生成部门总库发布文件。
4. 默认文件包含完整部门总表、版本基线、显式删除标记和必要审计结果，同时包含本次统一更新结果。
5. 将文件发布给所有需要更新的同事。

发布的是新的完整部门总数据文件，接收端采用增量合并；可选增量文件使用同样的规则。成员导入后直接获得独立的“部门总库 / 总表”，无需重新创建库，也不替换本机 SQLite 文件。

## 6. 成员接收部门总库更新

成员下载发布文件后：

1. 登录本机账号，导入文件并查看预览。
2. 系统按 `patent_uid` 和版本号计算本机新增、更新、冲突和已处理项目。
3. 部门统一字段和公共专利事实可以更新到本机部门总表。
4. 对个人库中存在相同 `patent_uid` 的记录，按字段映射同步对应更新。
5. 个人独有字段、个人备注和未授权字段保持不变。
6. 本机存在未提交修改时，不直接覆盖，生成本地冲突待处理项。
7. 应用成功后记录发布文件版本和本机应用结果。

“同步到个人细分库”采用按专利匹配、按字段更新：

- 总库更新了标题、申请号、法律状态等部门公共字段，个人库对应字段同步更新；
- 个人库有自己的分类、备注、任务状态等字段，除非明确配置为部门统一字段，否则不被总库覆盖；
- 个人库有该专利但总库没有本次变更时，不做无关修改；
- 个人库没有该专利时，不自动加入该细分库，仅新增到部门总表；成员可自行加入个人库。

公共字段可以通过本机统一专利主记录在多个库中展示，无需重复复制；库内专属字段独立保存。总表和个人库回写在同一批次提交并保留同步前备份，应用失败则回滚。系统记录变更的原始 ID 和来源，成员再次导出时不能把已接收的部门更新冒充为本人新修改反复回传。

## 7. 同事之间互相导入特定库

同事之间的导入流程与部门汇总相同，但目标范围更小：

1. 发送方选择一个特定数据库，生成完整快照或增量文件。
2. 接收方选择文件并预览，系统检查目标库导入权限。
3. 确认后直接建立或更新本机的“来自某同事的共享库”，保留原库 UID 和创建者。
4. 再次导入同一来源库时更新已有共享库，不重复建立副本。
5. 接收方也可以选择合并到个人库，此时保留来源和字段映射。

### 7.1 他人编辑的特别处理

如果接收方编辑了他人导入的记录，系统必须同时保存：

- 原始来源人和来源数据库；
- 原始值；
- 接收方修改后的值；
- 修改人、修改时间和修改原因；
- 该修改是否已回传原数据库或部门总库。

界面上至少区分“本人编辑”“他人编辑”“部门已确认”三种状态。接收方的修改可以作为新的增量变更导出，但不能伪装成发送方原始修改。原记录和后续编辑都保留在审计中。

他人编辑使用独立变更层：原创建者的数据作为来源基线，接收方修改另存，界面展示基线和本地修改后的结果。后续收到创建者的新文件时，先更新来源基线，再合并独立变更；同字段不同修改形成冲突。这些变更回传后由创建者或部门管理员确认，不能自动覆盖创建者原库。

### 7.2 编辑权限建议

- 只有查看权限：可以阅读，不能修改；再导出仍需导出权限。
- 有导入权限：可以把共享记录导入共享库或个人库，形成可追踪的本地版本。
- 有协作编辑权限：可以编辑共享记录，但每个字段必须带编辑人和审计记录。
- 部门管理员：可以在总库中确认最终值，并决定是否发布给全员。

## 8. 冲突审计要求

冲突审计不是错误日志，而是每周汇总的一部分。至少需要记录：

| 审计项 | 内容 |
|---|---|
| 批次 | 哪一次周汇总或哪一个导入文件 |
| 数据对象 | 专利、数据库和字段的稳定 ID |
| 参与来源 | 哪些同事、哪些数据库提交过变更 |
| 基线版本 | 每个变更基于哪个版本产生 |
| 候选值 | 各来源提交的值 |
| 最终决定 | 保留、接受、手工合并或暂缓 |
| 处理人和时间 | 谁在什么时候作出决定 |
| 后续动作 | 是否已经发布、回传或仍待处理 |

审计记录追加写入，不因为下一周再次同步而删除。重复文件只标记为“已处理”，不重复产生业务变更。

## 9. 异常和边界处理

- **同一文件重复导入**：识别 `package_id` 和 `change_uid`，显示已处理，不重复更新。
- **成员漏交本周文件**：管理员发布总库时保留上周结果，不自动删除该成员原有数据。
- **成员离职或账号停用**：停用账号和导出权限；历史变更仍保留原工号和姓名。
- **删除数据**：退出个人库仅同步该库成员关系变化，不删除部门专利或其他同事数据。部门记录删除须管理员确认，成员个人库有独立工作内容时保留记录并标记总库已删除，不级联清除。
- **版本过旧**：允许先预览，要求基于最新总库重新导出或由管理员人工处理。
- **字段定义变化**：先提示字段不兼容，不能把新字段静默写入旧字段。
- **导入失败**：保留原数据库不变，生成失败报告和可重试文件。

## 10. 一周操作节奏

```text
周一至周四：每个人在本地工作、导入、标注和维护个人库
周五截止前：成员勾选预设共享库并生成整库数据文件
周五/周末：管理员汇总、处理冲突、统一更新需更新的专利
发布日：管理员生成新的部门总库发布文件
下周开始：成员导入发布文件，更新总表和个人细分库
```

## 11. 产品实现优先级

第一阶段只实现能支撑上述闭环的功能：

1. 账号清单导入、登录和启停用；
2. 数据库级查看、导出、导入和管理员汇总权限；
3. 完整快照和基于检查点的增量文件；
4. 稳定专利 ID、变更 ID、版本和删除标记；
5. 管理员汇总预览、自动合并和冲突审计；
6. 部门总库发布和成员本地回写；
7. 共享库导入以及“本人编辑/他人编辑/部门确认”状态；
8. 重复导入、断点失败和备份恢复。

以下内容不属于本方案的必要条件，可后续再评估：实时在线同步、复杂 Token 体系、设备签名、中央服务器、自动跨部门权限继承和整库覆盖更新。

## 12. 验收标准

使用管理员、成员 A、成员 B 三个账号进行验收：

- A 能导出自己选择的两个数据库整库，管理员能看到来源和范围；
- A 第二次导出完整文件，管理员仅应用变化，重复导入不会产生重复记录；
- 不同 UID 的同一专利能按号码建立映射，不重复新增；同族不同专利保持独立；
- 管理员汇总后能按预设范围统一更新专利，并保留外部更新来源；
- A、B 同时修改同一专利同一字段时，总库不静默覆盖，并生成冲突审计；
- 管理员处理冲突后能发布新的总库文件；
- A 导入总库文件后，部门总表更新，A 的个人细分库中对应专利同步更新；
- A 的个人备注等非统一字段不被总库覆盖；
- 个人库移除某专利不会导致部门总库删除，文件省略字段不会清空本机值；
- 漏同步几周后可直接导入完整总库文件，获得当前部门总表；
- A 导入 B 的特定库后，B 的原始值、A 的修改值和两人的身份都能区分；
- B 再次发布库文件时，A 的独立编辑仍保留，出现差异能审计；
- 没有导入权限的账号无法写入目标数据库；
- 任一导入失败时，目标数据库保持导入前状态，并可查看失败原因。
