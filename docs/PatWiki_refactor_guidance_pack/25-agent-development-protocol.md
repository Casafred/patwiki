# 25 - PatWiki Agent 开发协议

> 状态：`agent-executable / mandatory`
> 更新：2026-08-15
> 本文面向执行开发任务的 Agent，不是给人阅读的背景介绍。Agent 开始任何代码、数据库、导入、详情页、表格、导出或交互改动前，必须按本文执行。

## 1. Agent 的唯一当前任务目标

PatWiki 当前不是全面 IP 工作流平台。Agent 的首要目标是交付：

**以每篇专利为锚点、可随手录入和持续积累、可完整查询调用、可追溯、可生成 Excel/Word 工作文件的本地交互数据库。**

当前默认运行边界：单人、本地、Tauri + React/Vite + FastAPI + SQLAlchemy + SQLite。除非用户明确改变范围，Agent 不得主动引入云端、跨设备、多人权限、ERP/PLM/代理系统集成或完整 Docket 工作流。

4. `README.md`：文档索引与冲突处理入口。

### 2.3 文档优先级

出现冲突时按以下顺序解释：

1. 用户最新明确确认的业务事实；
2. `23-2026-product-scope-and-business-rules.md`；
3. `21-implementation-contract.md`；
4. `24-patent-information-hub-functional-spec.md` 和 `26-human-data-entry-interaction-spec.md`；
5. `16-field-governance-registry.md`、`15-domain-model-v2.md`、`20-migration-roadmap.md`；
6. 其他长期设计文档；
7. 当前代码行为只能作为待修正的实现事实，不能作为业务规则依据。

如果规则缺失，Agent 必须先选择“保留来源、保存草稿、待确认”的可逆路径，不得自行创造不可逆语义。若无法安全实现，必须明确指出缺少的业务决策和影响范围。

## 3. 标准任务循环

每次任务按以下顺序执行，并在最终报告中逐项说明：

1. **分类范围**：判断属于 P0 专利信息中心、P1 专利关联能力，还是长期延后能力；主动排除超出范围的部分。
2. **读取规范**：完成 2.1 和 2.2 的文档读取，记录实际采用的章节。
3. **检查代码事实**：定位现有模型、服务、API、页面、迁移和测试；不得假设文档所述能力已经实现。
4. **定义数据路径**：写明输入、身份、字段状态、来源观察、当前采用值、审计和失败处理；未知属性必须遵守 `unmapped_retained` 规则。
5. **先补规则再写代码**：若交互、字段语义、状态或数据关系在文档中没有定义，先更新权威 Markdown/CSV，再实现。
6. **最小闭环实现**：模型/迁移、服务、API、前端、导入/导出和测试必须形成可用闭环；不能只做空 UI 或只做表结构。
7. **按场景验证**：至少覆盖正常路径、重复导入、空值/部分录入、冲突、撤销/恢复、来源追溯和未知属性路径。
8. **复核范围**：检查是否误覆盖人工数据、是否把草稿当正式结论、是否增加了不必要的复杂工作流。
9. **交付报告**：说明改动文件、文档依据、测试命令与结果、未完成项和需要用户确认的问题。

### 3.1 当前 G0 任务执行要求

涉及未知属性、导入治理或来源追溯时，Agent 必须先检查 `DEVELOPMENT_PROGRESS.md` 的 G0 状态和 `21-implementation-contract.md` 的 4.0 节。实现顺序固定为：

1. 先完成服务层决策和事务边界；
2. 再补 API schema、回归测试和导出；
3. 最后实现工作台，不允许只做页面状态而绕过服务层；
4. 每次将未知属性升级为正式字段前，必须明确字段名称、类型、责任人、来源范围和统计口径；缺一项只能保留为来源专用字段或候选字段。

Agent 不得以“用户已经看到 CSV”为理由跳过确认、回填、历史和失败重试。当前 G0 首版已经提供四类治理动作和稳定决策历史 API，但撤销最近治理批次、可视化历史面板和分页尚未完成，必须按 `DEVELOPMENT_PROGRESS.md` 的 G0-8 继续实现，不得在交付报告中声称这些能力已存在。

### 3.2 当前治理接口执行清单

当任务涉及待治理属性时，Agent 必须按以下顺序实现和验证：

1. 队列读取使用 `GET /import/unmapped`，默认状态是 `unmapped_retained`；完整来源审计使用 `GET /import/unmapped/export`，默认状态是 `all`，不得把完整导出误当成待处理队列。
2. 决策只能通过 `PATCH /import/observations/{observation_id}`；前端不得直接写 `Patent`、`Patent.custom_fields`、`FieldObservation` 或自行伪造历史。
3. 批量动作必须将影响范围固化为 `ImportBatch + source_field_name`，响应返回 `updated_count` 和 `adopted_value_count`，前端明确展示这两个数字。
4. 对 `map_existing` 同时验证 Field Registry、采用来源值开关、空值不覆盖和 `PatentHistory(source=governance)`；对 `retain_source`/`ignore` 验证观察记录仍存在并能在 `status=all` 导出中出现。
5. 每次新动作至少增加：单条路径、批量边界路径、原始证据保留路径、决策历史路径和失败重试路径测试；没有这些测试不能标记完成。

## 4. 不可违反的开发规则

- 未知列、未知属性或暂时无法归类的信息不能静默丢弃，不能未经治理写入正式字段、默认统计或 `Patent.custom_fields`。
- 可解析且身份可保留的输入进入 `unmapped_retained`；只有损坏、解析失败、身份冲突或完整性错误进入 `quarantined`。
- 外部导入不能静默覆盖人工分类、分析、风险、保护和内部关系；空单元格默认表示“不修改”，不是清空。
- 来源观察、候选规范值和当前采用值必须分离；相同值也必须记录来源观察。
- 专利申请号、公开号和授权号必须按身份规则归并；同族成员只关联不合并。
- 多值关系不能用逗号文本、JSON ID 数组或页面临时字段代替关系实体。
- 正式风险、正式决策和人工确认值不能由 AI 或前端直接签发；必须经过服务层校验和审计。
- 迁移不能继续依赖吞异常的容错加列；复杂拆分、回填和索引必须进入版本化迁移和备份门禁。
- 不得为了“方便”把所有业务对象塞进专利表或自定义字段；字段位置必须有 Field Registry 依据。
- 不得用大规模重写 UI、重命名主表或引入长期平台能力阻塞专利信息中心。

## 5. Agent 交付完成定义

### 5.1 数据完整性

- 任一新增值都能追溯到操作者/批次、时间、来源和原始值；
- 用户只录入部分信息时可以保存草稿，后续可以继续编辑；
- 空值不会意外清空已有值；批量修改有范围、预览、审计和撤销/恢复路径；
- 未知属性可查询和导出，后续映射不会删除原始观察；
- 重复导入幂等，身份冲突和内容冲突不会静默合并。

### 5.2 交互可用性

- 高频录入不要求用户先完成复杂主数据配置；
- 已知专利可以从详情页直接编辑，未知专利可以先进入待补身份 Inbox；
- 可用键盘完成新增、保存、取消、下一项、复制和批量粘贴；
- 用户能明确看到“已保存/草稿/冲突/待治理/失败”，不能只依赖 Toast 或颜色；
- 录入失败时保留输入并提供修正后重试，不要求重新输入整行。

### 5.3 工程验证

- 运行与改动相关的后端、前端、迁移和导入测试；
- 新增业务规则必须有自动化测试或可重复验收脚本；
- 执行 `git diff --check`；
- 文档、CSV、Schema 与代码引用保持一致；
- 最终报告列出未运行的测试和剩余风险，不得声称未验证的能力已完成。

## 6. 需要暂停并请求确认的情况

Agent 只有在下列情况暂停请求用户确认：

- 删除或不可逆覆盖真实数据；
- 业务规则会改变正式风险、保护、分类或统计含义；
- 需要把未知属性直接升级为正式字段，但语义、责任人或统计口径不明确；
- 需要引入云端、跨设备、多人权限、外部系统连接等超出当前边界的能力；
- 现有用户改动与任务发生实质冲突，无法在不丢失改动的前提下继续。

普通字段缺失、来源未知或数据不完整不构成暂停理由：应按草稿、来源观察或 `unmapped_retained` 路径继续保留。

## 7. 最终报告格式

Agent 完成任务时必须输出：

1. 结果：完成了什么，是否改变了当前产品行为；
2. 文档依据：读取和遵循了哪些文件/章节；
3. 文件改动：模型、服务、API、UI、测试、文档分别列出；
4. 验证：实际执行的命令和结果；
5. 未完成与风险：明确未实现、未验证和需要确认的事项。
